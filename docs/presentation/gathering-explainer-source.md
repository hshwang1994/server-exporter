| 개념 | 설명 |
|---|---|

## 1. 이 시스템이 푸는 문제 [개괄]

**상황**: 데이터센터에 서버가 수백 대 있다. 각각 CPU 몇 개인지, 메모리 몇 GB인지, 디스크가
몇 개 붙어 있는지, 펌웨어 버전이 몇인지 알아야 한다. 사람이 한 대씩 들어가 확인하는 것은
현실적이지 않고, 확인하는 사람마다 기록 형식도 달라진다.

**이 시스템이 하는 일**: 장비 주소 목록만 넘기면 자동으로 접속해 정보를 캐 오고, **제조사가
달라도 똑같은 모양의 JSON**으로 정리해 돌려준다.

### 왜 접근 경로가 3가지인가

한 가지 방법으로는 모든 상황을 못 덮는다. 목적에 따라 물어볼 상대가 다르다.

| 경로 | 누구에게 묻는가 | 언제 쓰는가 | 한계 |
|---|---|---|---|
| **운영체제 경로** | 서버에 설치된 리눅스/윈도우 | 실제로 운영체제가 인식하는 값(마운트된 디스크, 실제 IP 설정 등)이 필요할 때 | 서버가 켜져 있고 운영체제가 살아 있어야 함 |
| **가상화 호스트 경로** | 가상 서버를 돌리는 호스트 | 가상화 환경의 저장소·네트워크 구성이 필요할 때 | 가상화 전용 통로가 열려 있어야 함 |
| **관리 칩 경로** | 서버 관리 칩 | 하드웨어 실물 정보(부품 일련번호, 펌웨어, 전원, 온도)가 필요할 때. **본체가 꺼져 있어도 가능** | 운영체제 안쪽 정보는 못 봄 |

같은 서버라도 무엇을 알고 싶은지에 따라 다른 경로로 물어야 한다. 그래서 3가지를 다 만들었다.

### 핵심 가치 한 줄

> 제조사가 Dell이든 HPE든 Lenovo든, **받는 쪽이 보는 결과 모양은 하나**다.
> 새 제조사가 들어와도 코드를 고치지 않고 설정 파일 하나만 놓으면 된다.

## 2. 전체 큰 그림 [개괄]

요청부터 결과 회신까지 큰 줄기는 **갈림길 없는 직선**이다. 갈림길은 이 줄기 안쪽에서 생긴다.

```
요청자(포털)  →  자동 실행 서버  →  자동화 도구  →  대상 장비들  →  결과 회신(포털)
```

1. **요청자**가 "어느 위치의, 어떤 종류 장비를, 이 주소 목록으로 수집해 달라"고 요청한다.
2. **자동 실행 서버**가 요청을 검증하고 작업을 시작한다.
3. **자동화 도구**가 대상 종류에 맞는 작업 절차서를 골라 장비들에 접속한다.
4. **대상 장비들**에서 정보를 캐 온다. 여러 대를 동시에 처리한다.
5. 결과를 정해진 JSON 모양으로 정리해 **요청자에게 돌려준다**.

> **작도 참고**: 이 5단계 자체에는 분기·반복이 없다. 이 그림은 "가장 바깥 껍데기"로만 쓰고,
> 실제 분기는 3장(파이프라인 내부), 4장(대상 종류 분기), 5~7장(경로별 내부)에서 그린다.

## 3. 자동 실행 파이프라인 (포탈 연동용) [심화]

근거: `Jenkinsfile_portal` (355줄 전체)

이 파일이 요청을 받아서 결과를 돌려주기까지의 전 과정을 정의한다.

### 3-1. 요청자가 넘기는 값 6개

| 값 | 무엇인가 | 근거 |
|---|---|---|
| `loc` | 어느 위치의 현장 실행 서버를 쓸지 (ich / chj / yi) | `:6-10` |
| `target_type` | 대상 종류. **os / esxi / redfish 중 하나만** 허용 (선택지로 고정) | `:11-15` |
| `inventory_json` | 대상 장비 주소 목록 (JSON 배열) | `:16-19` |
| `deploymentEnvironmentId` | 포털 쪽 환경 식별자. 결과에 그대로 실어 보낸다 | `:20-24` |
| `callbackUrl` | 결과를 보낼 주소 | `:25-29` |
| `verbosity` | 로그 상세도 (0~4) | `:30-34` |

### 3-2. [작도 필수] 실행 위치가 두 곳으로 나뉜다

이 파이프라인은 **전체를 한 서버에서 돌리지 않는다**. 단계마다 실행 위치를 따로 지정한다
(`:3` 에서 기본 실행 위치를 지정하지 않고, 단계별로 선언).

| 단계 | 실행 위치 | 저장소 파일 내려받기 | 근거 |
|---|---|---|---|
| 1. 검증 | **현장 실행 서버** (`loc` 로 지정) | 안 함 (파일이 필요 없음) | `:51-61` |
| 2. 수집 | **현장 실행 서버** | 함 | `:119-126` |
| 3. 결과 형식 검증 | **현장 실행 서버** | 함 | `:202-209` |
| 4. 결과 회신 | **중앙 서버** (`built-in`) | 안 함 | `:227-232` |

**왜 나누는가**: 수집은 대상 장비와 같은 망에 있는 현장 서버에서만 가능하고, 포털로 결과를
보내는 것은 중앙 서버에서만 가능하다. 망이 분리돼 있기 때문이다.

**그래서 생기는 문제와 해결**: 실행 위치가 다르면 파일을 그냥 넘길 수 없다. 그래서 수집 결과
파일을 **보관해 두었다가**(`:187-191`) 회신 단계에서 **꺼내 쓴다**(`:235`).

또 각 단계는 끝나면 작업 폴더를 지운다(`:193-197`, `:218-222`, `:328-332`).

> **작도 참고**: 흐름도에 **세로 점선으로 "현장 실행 서버 | 중앙 서버" 경계**를 그리고,
> 2단계에서 4단계로 넘어갈 때 그 선을 넘는 "파일 전달" 화살표를 별도로 표시해야 한다.

### 3-3. 1단계 — 검증 (직선형 + 조기 종료)

파라미터만 본다. 저장소 파일은 읽지 않는다. **9가지를 순서대로 확인하고, 하나라도 걸리면
그 자리에서 전체를 중단**한다.

| 순서 | 확인 내용 | 근거 |
|---|---|---|
| 1 | 위치 값이 비어 있지 않은가 | `:64-66` |
| 2 | 대상 종류가 os/esxi/redfish 중 하나인가 | `:68-71` |
| 3 | 주소 목록이 비어 있지 않은가 | `:73-75` |
| 4 | 주소 목록이 올바른 JSON인가 | `:78-82` |
| 5 | JSON 배열에 항목이 1개 이상 있는가 | `:84-86` |
| 6 | **각 항목에 주소가 들어 있는가** (아래 4장 참조) | `:88-95` |
| 7 | 회신 주소가 비어 있지 않고 `http://` 또는 `https://` 로 시작하는가 | `:97-103` |
| 8 | **회신 주소에 따옴표·역따옴표·역슬래시·공백이 없는가** | `:104-106` |
| 9 | 포털 환경 식별자가 비어 있지 않은가 | `:107-109` |

8번은 보안 방어다. 회신 주소는 나중에 명령에 섞여 들어갈 수 있으므로, 명령을 조작할 수 있는
문자가 들어오면 아예 거부한다.

> **작도 참고**: 이 구간은 **세로 일직선에 9개 마름모(판정)를 쌓고, 각 마름모의 "아니오"가
> 모두 하나의 "중단" 노드로 모이는** 형태다. "예"는 아래로 계속 이어진다.

### 3-4. 2단계 — 수집

작업 폴더 이름을 단계마다 동일하게 쓰고(`:54`, `:122`, `:205`), 이 단계에서만 아래 값들을
환경에 설정한다(`:127-132`).

| 환경값 | 역할 |
|---|---|
| `REPO_ROOT` | 저장소 위치. 절차서가 다른 파일을 찾을 때 기준으로 쓴다 |
| `ANSIBLE_CONFIG` | 자동화 도구 설정 파일 위치 |
| `ANSIBLE_JSON_OUTPUT_FILE` | **수집 결과를 쌓을 파일 위치** |
| `ANSIBLE_VERBOSITY` | 로그 상세도 |

실행 순서:

1. **대상 종류로 작업 절차서와 대상 목록 스크립트를 고른다**(`:135-147`). 자세한 것은 4장.
2. **이전 결과 파일을 지운다**(`:150`). 결과 파일이 "덧붙이기" 방식이라, 안 지우면 지난
   실행 결과가 섞인다.
3. 금고 암호를 꺼내(`:158-163`) **임시 파일에 쓰고 권한을 잠근 뒤**(`:170-173`), 작업이
   끝나면 자동 삭제되도록 걸어 둔다(`:171`).
4. 자동화 도구를 실행한다(`:174`).
5. **결과 파일이 만들어졌는지 확인한다**(`:181-184`).
6. 결과 파일을 보관한다(`:187-191`).

#### [작도 필수] 실행 명령의 특이점 2가지

**① 대상 목록은 명령 인자가 아니라 환경변수로 넘어간다.**
실제 실행 명령은 이것뿐이다(`:174`):

```
ansible-playbook <절차서> -i <대상목록 스크립트> --vault-password-file=<임시 암호파일>
```

장비 주소는 여기 없다. 파이프라인 맨 위에서 환경변수로 넣어 두고(`:38`), 대상 목록 스크립트가
실행될 때 그 환경변수를 읽어 주소 목록을 만든다. 흐름도에서 **"주소 목록"은 명령 화살표가
아니라 옆에서 들어오는 별도 입력**으로 그려야 정확하다.

**② 실패 처리가 두 갈래다.**

## 4. 대상 종류에 따른 분기 — 갈림길은 총 4곳 [심화]

"os / esxi / redfish 중 무엇이냐"가 한 곳에서만 갈리는 게 아니라 **파이프라인 안에서 4번 갈린다**.

| # | 어디서 | 무엇이 갈리는가 | 근거 |
|---|---|---|---|
| ① | 입력 정의 + 검증 | 셋 중 하나가 아니면 **즉시 중단** | `:11-15`, `:68-71` |
| ② | 검증 중 주소 확인 | **어느 항목 이름에서 주소를 찾을지** | `:88-95` |
| ③ | 수집 단계 시작 | **어떤 작업 절차서와 대상 목록 스크립트를 쓸지** | `:135-147` |
| ④ | 회신 주소 조립 | 회신 주소 **끝에 붙는 경로** | `:238` |

### 4-1. 갈림길 ② — 주소 항목 이름

관리 칩은 본체와 **주소가 다르다**. 그래서 항목 이름이 다르다.

```
대상 종류가 redfish 이면  →  "bmc_ip"     (관리 칩 주소)
그 외(os, esxi) 이면      →  "service_ip" (서버 본체 주소)
둘 다 없으면              →  "ip"         (공통 예비 이름)
그것도 없으면             →  중단
```

근거: `:88-95`. 조건문 한 줄로 이름을 고르고, 없으면 예비 이름으로 넘어가는 2단 구조다.

### 4-2. 갈림길 ③ — 절차서 선택 (조건문이 아니라 표 조회)

이 부분이 설계상 눈여겨볼 곳이다. `if 대상종류 == 'os' then ... else if ...` 방식이 아니라,
**미리 만든 표에서 값을 꺼내는 방식**이다(`:135-147`).

| 대상 종류 | 작업 절차서 | 대상 목록 스크립트 | 주소 항목 이름 |
|---|---|---|---|
| `os` | `os-gather/site.yml` | `os-gather/inventory.sh` | `service_ip` → 없으면 `ip` |
| `esxi` | `esxi-gather/site.yml` | `esxi-gather/inventory.sh` | `service_ip` → 없으면 `ip` |
| `redfish` | `redfish-gather/site.yml` | `redfish-gather/inventory.sh` | `bmc_ip` → 없으면 `ip` |

> **설명 포인트**: 표 조회 방식이라 대상 종류가 늘어나도 조건문이 길어지지 않는다.
> 이 "조건문 대신 표/데이터" 사고방식이 12장(새 장비 추가)에서 훨씬 큰 규모로 다시 나온다.

### 4-3. 대상 목록 스크립트 3벌은 거의 같다

3개 파일은 **주소 항목 이름 한 곳만 다르고 나머지는 동일**하다
(`os-gather/inventory.sh:86`, `esxi-gather/inventory.sh:86` = `service_ip` /
`redfish-gather/inventory.sh:88` = `bmc_ip`).

공통 동작:
1. 환경변수에서 주소 목록 JSON을 읽는다 (없으면 소문자 이름으로 재시도, 그래도 없으면 중단).
2. 배열인지, 비어 있지 않은지 확인한다.
3. 각 항목에서 주소를 꺼내고 **IPv4 형식이 맞는지 검사**한다.
4. **주소 중복이 있는지 검사**한다.
5. 자동화 도구가 이해하는 목록 형태로 출력한다.

**계정 정보는 이 목록에 들어가지 않는다.** 계정은 금고에서 따로 꺼낸다.

### 5-5. [작도 필수] 리눅스의 큰 분기 — 파이썬이 있느냐

리눅스는 오래된 서버가 많다. 자동화 도구는 보통 대상 서버의 파이썬을 쓰는데, 파이썬이 없거나
너무 낡으면 표준 방식이 통하지 않는다. 그래서 **수집 방식이 두 갈래**로 갈린다.

사전 점검이 결정하는 4가지 상태(`os-gather/tasks/linux/preflight.yml:57-65`, 우선순위 순):

| # | 상태 | 조건 |
|---|---|---|
| 1 | 강제 원시모드 | 환경변수로 강제 지정됐을 때 (개발·검증용) |
| 2 | 파이썬 없음 | 파이썬 실행 파일을 못 찾았거나 버전을 못 읽었을 때 |
| 3 | **파이썬 정상** | 파이썬 **3.9 이상** |
| 4 | 파이썬 구버전 | 3.8 이하 |

**갈래는 2개다**: 3번만 "표준 방식", **1·2·4번은 모두 "원시 방식"으로 합류**한다.
각 수집 파일이 `상태 == 파이썬 정상` 과 `상태 != 파이썬 정상` 두 덩어리로 나뉘어 있기 때문이다.

- **표준 방식**: 자동화 도구의 정보 수집 기능, 셸 명령, 계정 조회 기능 등을 쓴다.
- **원시 방식**: 대상 서버에서 아무 것도 설치하지 않고 **가장 원시적인 명령만** 보내고,
  결과 해석은 전부 **작업을 지시하는 쪽(현장 실행 서버)에서** 한다.

> **작도 참고**: 마름모 하나에서 **4갈래로 갈렸다가 즉시 2갈래로 합류**하는 그림이 정확하다.
> 단순히 "파이썬 있음/없음" 2갈래로 그리면 강제 지정·구버전 케이스가 사라진다.

### 7-2. [설명 포인트] 왜 계정 없이 먼저 묻는가

계정을 꺼내려면 **어느 금고를 열지** 알아야 한다. 금고는 제조사별로 나뉘어 있다
(`vault/redfish/` 아래 9개: cisco, dell, fujitsu, hpe, huawei, inspur, lenovo, quanta, supermicro).
그런데 제조사를 알려면 장비에 물어봐야 한다. 순환이다.

해결책: **관리 칩 표준 규격은 "나는 누구인가"를 인증 없이 답하도록 정해 놓았다.**
그래서 1차로 계정 없이 물어 제조사를 확인하고(`tasks/detect_vendor.yml:12-22`),
그 결과로 금고를 정하고, 2차로 인증해서 본 수집을 한다.

이 1차 조회는 **실패해도 전체를 중단시키지 않는다**(같은 파일 `:12-22`). 못 알아내면 이후
범용 설정표로 넘어간다.

제조사 이름은 표기가 제각각이라(`Dell` / `Dell Inc.` / `Dell EMC` 등) 별도 표준화 표
(`common/vars/vendor_aliases.yml`)로 통일한다. 완전 일치 → 부분 일치 순으로 맞춘다
(`detect_vendor.yml:24-77`).

### 7-3. [작도 필수] 계정 순차 시도 — 대기가 들어간 반복

금고에서 꺼낸 계정을 **하나씩 순서대로** 시도한다(`tasks/collect_standard.yml:52-60`).

```
계정 목록의 첫 번째부터:
   접속해서 수집 시도
   성공하면 → 어느 계정으로 성공했는지 기록하고 반복 종료
   실패하면 → 5초 쉬고 → 다음 계정
계정이 아예 0개면 → 계정 없이 1회 시도
전부 실패하면 → 중단
```

근거: `tasks/try_one_account.yml:21-34`(시도), `:51-62`(성공 기록), `:84-88`(5초 대기).

> **왜 5초를 쉬는가**: 관리 칩은 비밀번호를 연속으로 틀리면 계정을 잠근다. 쉬지 않고 여러
> 계정을 빠르게 시도하면 계정이 잠겨 버린다.

> **작도 참고**: 되돌아가는 화살표에 **"실패 시 5초 대기"** 를 반드시 표기한다.

### 7-4. [작도 필수] 조건부 되돌아가기 — 계정 복구

계정 목록에는 평상시 쓰는 계정과 **비상용 복구 계정**이 섞여 있다.
**복구 계정으로 성공한 경우에만**(`:117-121`) 아래를 수행한다:

```
평상시 계정을 관리 칩에 다시 만든다  →  성공하면 수집을 처음부터 다시 한다
```

### 7-5. [작도 필수] 제조사 전용 수집은 실패해도 전체를 죽이지 않는다

설정표에 "제조사 전용 수집 절차"가 적혀 있을 때만 이 단계가 실행된다(`:137-162`).

> **왜 이렇게 했나**: 표준 수집이 다 성공했는데 제조사 전용 추가 정보 하나 때문에 전체가
> 실패로 뒤집히는 사고가 있었기 때문이다(`:130-136` 주석).

> **작도 참고**: 이 상자만 **점선 테두리로 감싸고 "실패해도 통과"** 라고 표기.

### 7-6. 수집 도구 내부에서 일어나는 일

이 경로의 실제 수집은 자체 제작 도구 하나가 전담한다

## 9. 결과가 하나로 합쳐지는 원리 — 조각 모으기 [심화]

### 9-1. 풀어야 했던 문제

경로가 3개이고, 각 경로 안에 수집 단계가 10개 안팎이다. 이 수십 개가 각자 결과를 만드는데,
**최종 결과의 모양은 하나여야 한다**. 각 단계가 최종 결과를 직접 고치게 하면, 나중에 누가 무엇을
덮어썼는지 추적이 불가능해진다.

### 9-2. 해결 방식 — 4단 구조

```
① 빈 뼈대 만들기  →  ② 각 단계가 "자기 조각"만 만들기  →  ③ 병합 장치가 누적  →  ④ 조립기들이 최종 결과
```

**① 빈 뼈대**(`common/tasks/normalize/init_fragments.yml:39-80`)
시작할 때 11가지 항목의 자리를 미리 만들어 둔다. 값이 들어올 자리는 비어 있지만 **자리 자체는
있다**. 목록이 들어올 곳은 빈 목록, 단일 값이 들어올 곳은 빈 값으로 초기화한다.

**② 자기 조각만**
각 수집 단계는 최종 결과를 건드리지 않고, **6가지만** 만든다(`merge_fragment.yml:26-45`):
자기가 캐 온 값 / 자기가 지원하는 항목 목록 / 성공한 항목 목록 / 실패한 항목 목록 /
이 장비가 원래 안 가진 항목 목록 / 오류 목록.
**다른 단계의 몫은 절대 건드리지 않는다.**

**③ 병합 장치**(`common/tasks/normalize/merge_fragment.yml`)
각 수집 단계 직후에 호출돼서 조각을 누적 결과에 합친다. 합치는 규칙은 5가지다(`:72-107`):

| 상황 | 처리 |
|---|---|
| 새 조각에 값이 없음 | **기존 값 유지** |
| 기존에 값이 없음 | **새 값 채택** |
| 둘 다 사전(키-값 묶음) | **키 단위로 합침** — 새 값이 있는 키만 덮어쓰고 나머지는 유지 |
| 둘 다 목록 | **이어 붙임** (중복 제거 안 함) |
| 종류가 서로 다름 | **새 값 우선** |

> 사전 합치기는 **한 단계 깊이까지만** 적용된다. 더 깊은 구조는 통째로 교체된다.
> (코드 구조에서 도출한 해석 — **추정**)

그리고 **합치고 나면 조각 6가지를 전부 비운다**(`:110-118`). 안 비우면 다음 수집 단계가 이전
조각을 물려받아 남의 결과를 자기 것처럼 다시 합치게 된다.

> 항목 목록들은 **중복을 제거하며 합치고**(`:26-45`), 오류 목록은 형태가 제각각으로 들어와도
> `{항목, 메시지, 상세}` 모양으로 맞춰서 쌓는다. 과거에 오류 문자열이 글자 단위로 쪼개져
> 쌓이는 문제가 있어 방어 코드가 들어가 있다(`:41-45` 주석).

**④ 조립기들**
누적된 값을 최종 결과 항목으로 바꾸는 전담 파일들이다.

| 조립기 | 하는 일 | 파일 |
|---|---|---|
| 항목별 상태 | 11가지 항목 각각을 성공/실패/미지원으로 판정 | `build_sections.yml` |
| 전체 상태 | 성공/부분 성공/실패 하나로 요약 | `build_status.yml` |
| 오류 목록 | 오류들을 같은 모양으로 정리 | `build_errors.yml` |
| 실행 메타 | 시작·종료 시각, 소요 시간, 사용한 설정표 등 | `build_meta.yml` |
| 상관 식별자 | 일련번호·장비 고유 ID·주소 | `build_correlation.yml` |
| 최종 조립 | 위를 모아 하나의 결과 봉투로 | `build_output.yml` |

### 9-3. 항목별 상태 판정 — 우선순위가 있다

근거: `build_sections.yml:20-43`. 11가지 항목 각각에 대해 위에서부터 순서대로 본다.

```
미지원 목록에 있으면         →  미지원
지원 목록에 없으면           →  미지원
실패 목록에 있으면           →  실패
성공 목록에 있으면           →  성공
지원한다는데 아무 데도 없으면 →  실패
```

즉 **미지원 > 실패 > 성공** 순으로 강하다.

### 9-4. [설명 포인트] 전체 상태 판정

근거: `build_status.yml:51-66`. **미지원 항목은 계산에서 아예 뺀다.**

```
미지원을 뺀 항목이 하나도 없으면   →  실패
실패가 0개이면                     →  성공
성공이 0개이면                     →  실패
성공과 실패가 섞여 있으면          →  부분 성공
```

**중요한 설계 결정**: 전체 상태는 **항목 상태만 보고, 오류 목록은 보지 않는다**.
코드 안에 4가지 경우를 표로 적어 두었다(`build_status.yml:24-40`):

| 경우 | 항목별 상태 | 오류 목록 | 전체 상태 |
|---|---|---|---|
| A | 전부 성공 | 비어 있음 | **성공** |
| B | 전부 성공 | 경고 있음 | **성공** ← 주목 |
| C | 성공과 실패가 섞임 | 무관 | **부분 성공** |
| D | 전부 실패 | 무관 | **실패** |

**B가 핵심이다.** "전체 상태는 성공인데 오류 목록에 내용이 있는" 경우는 **정상**이다.
항목 자체는 다 잘 수집됐고, 오류 목록에 담긴 것은 "이런 경우라서 대체 방법을 썼다" 같은
사유 기록이기 때문이다. 코드 주석에도 의도된 동작이라고 명시돼 있다(`:33-40`).

> **설명 포인트**: 이 부분은 자료를 보는 사람이 가장 자주 오해하는 지점이다("성공인데 왜
> 에러가 있냐"). 장표에 위 표를 그대로 넣어 두는 것이 좋다.
> 받는 쪽에서 경고를 따로 다루고 싶으면 **전체 상태가 아니라 오류 목록을 직접 봐야 한다.**

## 10. 결과물이 실제로 어떻게 생겼는가 [심화]

근거: `common/tasks/normalize/build_output.yml:45-63` (구조) +
`schema/baseline_v1/dell_baseline.json` (실측 값)

### 10-1. 최상위 13개 항목

| # | 항목 | 무엇인가 | 실제 값 예시 |
|---|---|---|---|
| 1 | `target_type` | 어느 경로로 수집했나 | `"redfish"` |
| 2 | `collection_method` | 구체적 수집 방식 | `"redfish_api"` |
| 3 | `ip` | 접속한 주소 | `"10.50.11.162"` |
| 4 | `hostname` | 장비 이름 | `"LENOVO01"` |
| 5 | `vendor` | 제조사 (요청자에게 보여 줄 표기) | `"dell"` |
| 6 | `status` | 전체 결과 | `"success"` |
| 7 | `sections` | **항목별 상태 11개** | `{"system":"not_supported","hardware":"success",...}` |
| 8 | `diagnosis` | **어디까지 통했는지 진단 결과** | 아래 10-3 |
| 9 | `meta` | 실행 정보 | `{"started_at":...,"duration_ms":106000,"adapter_id":"redfish_dell_idrac9",...}` |
| 10 | `correlation` | 장비를 다른 시스템과 맞춰 볼 식별자 | `{"serial_number":"CNIVC009CP0282","system_uuid":"4c4c4544-...","bmc_ip":...,"host_ip":...}` |
| 11 | `errors` | 오류·경고 목록 | `[]` |
| 12 | `data` | **실제 수집한 내용 전부** | 아래 10-2 |
| 13 | `schema_version` | 결과 형식 버전 | `"1"` |

### 10-2. [설명 포인트] 수집 못 한 항목도 자리는 남는다

`sections` 에서 `not_supported` 인 항목도 **`data` 안에 키는 존재하고 값만 비어 있다.**

관리 칩 경로의 실제 결과에서, 운영체제 정보는 미지원인데 `data.system` 은 이렇게 생겼다:

```json
"system": {"os_family": null, "distribution": null, "version": null, "kernel": null,
           "architecture": null, "uptime_seconds": null, "selinux": null, "fqdn": "LENOVO01"}
```

목록이 들어갈 자리는 빈 목록이다: `"users": []`

> **왜 이렇게 했나**: 받는 쪽이 "이 키가 있나 없나"를 매번 확인하지 않아도 되게 하려고.
> **모양은 항상 같고 값만 비어 있다.** 9장의 "빈 뼈대"가 바로 이 자리를 만든다.

`data` 에 들어가는 11가지 항목:
시스템 / 하드웨어 / 관리 칩 / CPU / 메모리 / 저장소 / 네트워크 / 펌웨어 / 사용자 / 전원 / 온도.

저장소와 네트워크는 그 안에 또 여러 목록이 있다.
저장소: 파일시스템·물리 디스크·데이터스토어·컨트롤러·논리 볼륨·부가장치(HBA)·인피니밴드·요약.
네트워크: DNS 서버·기본 게이트웨이·인터페이스·어댑터·포트·가상 스위치·포트그룹·드라이버 목록·요약.

### 10-3. 진단 항목의 실제 모습

```json
"diagnosis": {
  "reachable": true, "port_open": true, "protocol_supported": true, "auth_success": true,
  "failure_stage": null, "failure_reason": null,
  "details": {"channel":"redfish", "adapter_candidate":"redfish_dell_idrac9",
              "checked_ports":[443], "selected_port":443,
              "redfish_version":"1.6.0", "product":"Integrated Dell Remote Access Controller",
              "systems_uri":"/redfish/v1/Systems"}
}
```

앞의 4개가 4단계 진단 결과다. 실패했다면 `failure_stage` 에 **어느 단계에서 막혔는지**가 들어간다.

### 10-4. 알아 둘 규칙 2가지

**① 장비 이름을 주소로 대체하지 않는다.**
장비 이름은 시스템 이름 → 전체 도메인 이름 → 관리 칩의 이름 순으로 찾고, **다 없으면 비워 둔다**
(`build_output.yml:32-43`, 정책 주석 `:28`). 주소를 이름 자리에 넣으면 받는 쪽이 진짜 이름과
주소를 구분할 수 없게 되기 때문이다.

**② 항목 순서는 경로마다 다르다. 순서에 의존하면 안 된다.**
정상 경로와 실패 경로에서는 `schema_version` 이 **맨 뒤**에 붙고, 최후 안전망 경로에서는
**맨 앞**에 온다. **키 13개는 항상 같지만 순서는 보장되지 않는다.**

### 10-5. 결과가 밖으로 나가는 방법

자동화 도구는 원래 실행 로그를 잔뜩 찍는다. 그대로 두면 요청자가 결과를 찾아낼 수 없다.
그래서 **출력 담당 부품**(`callback_plugins/json_only.py`, 157줄)이 다음을 한다:

- 이름이 **정확히 `OUTPUT`** 인 작업의 결과만 내보낸다(`:49`, `:108`).
  실제로 각 절차서의 마지막 작업 이름이 `OUTPUT` 이다(`os-gather/site.yml:180,361,553`,
  `redfish-gather/site.yml:256`, `esxi-gather/site.yml:252`).
- 시작/작업/건너뜀/요약 등 나머지 로그는 **전부 억제**한다(`:142-157`).
- 결과는 **장비 1대당 한 줄 JSON**으로 압축해서 출력한다(`:57-79`).
- 파일 경로가 지정돼 있으면 화면 출력과 **동시에 그 파일에 덧붙인다**(`:53`, `:81-92`).
- 오류·접속 불가는 표준 출력이 아니라 **에러 출력으로 보낸다**(`:117-138`). 결과 JSON이
  오염되지 않게 하기 위해서다.

> 이 때문에 결과 파일이 "한 줄에 JSON 하나씩" 쌓인 형태가 되고, 3-6절에서 그 줄들을 쉼표로
> 이어 붙여 배열로 만드는 것이다. **두 코드가 이 규칙으로 맞물려 있다.**

## 11. 실패해도 결과는 반드시 나온다 [심화]

이 시스템의 설계 원칙 중 하나는 **"어떤 경우에도 빈손으로 끝나지 않는다"** 이다.

### 11-1. 4단계 사전 진단 — 어디서 막혔는지 남긴다

근거: `common/library/precheck_bundle.py` (543줄)

본 수집 전에 4가지를 **순서대로** 확인한다. 앞이 안 되면 뒤는 확인할 의미가 없기 때문이다.

| 순서 | 확인 내용 | 확인 방법 |
|---|---|---|
| 1 | **도달 가능한가** | 주소를 IPv4/IPv6 양쪽으로 풀어 실제 연결을 시도 |
| 2 | **통로가 열려 있는가** | 대상별 통로에 순서대로 연결 시도, 첫 성공에서 멈춤 |
| 3 | **규격에 맞게 답하는가** | 실제로 요청을 보내 응답 형태 확인 |
| 4 | **인증이 되는가** | 계정으로 접속 시도 |

3번의 판정이 흥미롭다. **"200 정상 응답"만 성공으로 치지 않는다.** 인증 요구(401)나
권한 거부(403), 허용 안 된 방식(405), 일시적 과부하(503) 같은 응답도 **"규격은 통한다"로
인정**한다(`:291-299`). 그런 응답이 왔다는 것 자체가 상대가 그 규격을 이해한다는 뜻이기 때문이다.

대상별 통로(`:87-91`): 관리 칩 = 443 / 가상화 = 443 / 운영체제 = 5986, 5985, 22.

제한 시간: 통로 확인은 **3초**(빠르게 죽은 장비를 걸러내려고 일부러 짧게), 규격·인증 확인은
**30초**(`common/tasks/precheck/run_precheck.yml:35-37`).

#### [작도 주의] 이 진단 도구를 모든 경로가 쓰는 것은 아니다

**가상화 경로와 관리 칩 경로만 이 도구를 쓴다.** 운영체제 경로는 5-1절에서 본 것처럼
**통로 3개를 직접 두드리는 별도 방식**이다. 흐름도에서 두 방식을 같은 상자로 그리면 틀린다.

또 현재 관리 칩·가상화 경로는 이 도구에 계정을 넘기지 않아서 **4번(인증) 단계는 항상 건너뛴다**
(`redfish-gather/site.yml:41-47`, `esxi-gather/site.yml:46-52`). 실제 인증 성공 여부는 본 수집이
끝난 뒤 결과에 채워 넣는다(`redfish-gather/site.yml:191-193`, `esxi-gather/site.yml:200-210`).

### 11-2. 부분 성공 — 일부만 돼도 내보낸다

10가지를 물었는데 7가지만 답이 오면, 7가지를 담고 전체 상태를 **"부분 성공"** 으로 표시한다.
9-4절의 판정 규칙이 이것이다. 실패한 3가지가 무엇인지는 항목별 상태와 오류 목록에 남는다.

### 11-3. [작도 필수] 3중 안전망

세 경로 모두 같은 구조로 감싸져 있다.

| 계층 | 언제 | 무엇을 하나 |
|---|---|---|
| **1. 정상** | 수집이 정상적으로 끝남 | 정상 조립 → 13개 항목 결과 |
| **2. 중간 실패** | 수집 도중 예외 발생 | 어디서 실패했는지 기록하고 **실패용 조립기**로 13개 항목을 채움 |
| **3. 최후** | 위 둘 다 결과를 못 만듦 | **고정 형태로 13개 항목을 직접 채워** 내보냄 |

근거: 운영체제 경로 `os-gather/site.yml:339-357`(2계층) / `:359-377`(3계층),
가상화 경로 `esxi-gather/site.yml:230-248` / `:250-268`,
관리 칩 경로 `redfish-gather/site.yml:226-252` / `:254-272`.

2계층의 실패용 조립기(`common/tasks/normalize/build_failed_output.yml`)가 하는 일:
지원 목록에 있던 항목은 전부 **실패**로, 없던 항목은 **미지원**으로 표시 → 오류 1건 기록 →
전체 상태를 **실패**로 → 실행 정보·식별자가 이미 있으면 살리고 없으면 기본값 → 13개 항목 조립.

> **작도 참고**: 각 경로 흐름도를 **큰 상자 3겹으로 감싸고**, 안쪽에서 바깥으로 빠지는
> 화살표를 그리면 이 구조가 한눈에 보인다.

### 11-4. 격리된 실패 — 제조사 전용 단계

7-5절 참조. 관리 칩 경로의 제조사 전용 수집은 **자체 안전망**을 따로 갖고 있어서, 실패해도
2계층으로 넘어가지 않고 경고만 남긴다.

### 11-5. 조기 이탈 — 판별 실패 전용 경로

5-3절 참조. 운영체제를 못 알아낸 장비는 본 수집 자체를 건너뛰고 별도 단계에서 실패 결과만 만든다.

### 11-6. 실패 유형별로 요청자가 보게 되는 것

| 상황 | `status` | `diagnosis.failure_stage` | 결과 |
|---|---|---|---|
| 장비가 아예 응답 없음 | `failed` | 도달 단계 | 전 항목 실패/미지원, 오류 1건 |
| 통로가 막힘 (방화벽 등) | `failed` | 통로 단계 + 두드려 본 통로 목록 | 위와 동일 |
| 통로는 열렸는데 규격이 안 맞음 | `failed` | 규격 단계 | 위와 동일 |
| 계정이 전부 틀림 | `failed` | 인증 단계 | 위와 동일 |
| 일부 항목만 실패 | `partial` | 없음(`null`) | 성공한 항목은 값이 채워짐 |
| 전부 성공했지만 경고 있음 | `success` | 없음(`null`) | `errors` 에 경고가 담김 (9-4절) |

## 12. 새 장비가 들어오면 무엇을 하면 되는가 [심화]

**핵심 메시지: 코드를 고치지 않는다. 설정 파일을 놓는다.**

### 12-1. 3층 구조

| 층 | 무엇 | 규모 | 제조사 이름이 등장하는가 |
|---|---|---|---|
| **선언** | 장비별 설정표 (`adapters/` 아래 YAML) | **42개** | **여기에만** 있다 |
| **선택** | 설정표 선택기 (`lookup_plugins/adapter_loader.py` 270줄 + `module_utils/adapter_common.py` 354줄) | 2개 파일 | **하나도 없다** |
| **실행** | 작업 절차서 (경로별 `site.yml` 3벌) | 3개 | **하나도 없다** |

설정표 42개 내역(실측 2026-08-10): 관리 칩 경로 **31개**, 운영체제 경로 **7개**,
가상화 경로 **4개**.

> **설명 포인트**: 새 제조사가 들어와도 아래 두 층을 건드릴 일이 없다. 제조사 차이는 전부
> "데이터"로 표현돼 있기 때문이다.

### 12-2. 설정표에는 무엇이 들어 있나

| 구성 요소 | 내용 |
|---|---|
| **식별 정보** | 설정표 이름, 우선순위 |
| **적용 조건** | 어떤 장비에 이 표를 쓸지 (제조사·모델·펌웨어·버전·배포판·운영체제 종류 6가지) |
| **수집 가능 목록** | 이 장비에서 얻을 수 있는 항목들 |
| **수집 절차** | 표준만 쓸지, 제조사 전용까지 쓸지, 그 파일 경로 |
| **금고 지정** | 어느 금고를 쓸지, 실패하면 어느 금고를 대신 쓸지, 비상 복구 계정 목록 |
| **실패 정책** | 항목 실패 시 계속할지, 인증 실패 시 중단할지, 중요 항목 목록 |
| **안내 문구** | 미지원일 때 요청자에게 보여 줄 설명 |

### 12-3. [작도 필수] 설정표를 고르는 규칙 — 점수제

조건문으로 고르지 않는다. **모든 설정표를 훑어 점수를 매기고 최고점 하나를 고른다.**

```
① 폴더에서 설정표 파일을 전부 읽는다 (파일명 알파벳 순)
② 각 설정표의 적용 조건을 장비 정보와 맞춰 본다
③ 통과한 것들에 점수를 매긴다
④ 점수 순으로 정렬한다
⑤ 1등을 쓴다
```
근거: `lookup_plugins/adapter_loader.py:106`(읽기), `:126-171`(맞춰보고 점수), `:239-240`(정렬·선택).

**점수 공식** (`module_utils/adapter_common.py:336-354`):

```
점수 = 우선순위 × 1000  +  조건의 구체성 × 10  +  실제로 맞은 정도
```

| 항 | 뜻 | 값의 출처 |
|---|---|---|
| 우선순위 | 설정표에 사람이 직접 적어 둔 숫자 | 설정표의 `priority` |
| 조건의 구체성 | 조건을 몇 개나 걸었는가 | 제조사 +10, 모델 +20, 펌웨어 +20, 버전 +15, 배포판 +15, 운영체제 종류 +5 |
| 실제로 맞은 정도 | 그 조건들이 실제로 맞았는가 | 제조사 +20, 모델 +25, 펌웨어 +25, 버전 +15, 배포판 +15, 운영체제 종류 +5 |

**실측 검증 예시** (설정표 자체에 기록된 실제 측정값, `adapters/redfish/hpe_ilo7.yml:18-19`):
모델 `HPE ProLiant Compute DL380 Gen12`, 펌웨어 `1.20.00` 인 장비에서 점수 **120570** 으로 선택됨.
역산하면 `120×1000 + (10+20+20)×10 + (20+25+25) = 120000 + 500 + 70 = 120570`. 공식과 정확히 일치.

### 12-4. [작도 필수] 판정 규칙 3가지

이 셋이 이 설계의 핵심이다.

| 규칙 | 상황 | 처리 | 왜 |
|---|---|---|---|
| **① 실격** | 장비 정보가 **있는데** 조건과 다름 | **즉시 탈락** (아주 낮은 점수로 제외) | 명백히 다른 장비용 설정표를 쓰면 안 됨 |
| **② 관용** | 장비 정보가 **아예 없음** | **점수만 안 주고 탈락은 안 시킴** | 정보를 못 얻었다고 후보에서 빼면 쓸 설정표가 사라짐 |
| **③ 바닥** | 조건이 하나도 없는 **범용 설정표** | 항상 후보에 남되 **최하점**(−400) | 아무것도 안 맞을 때 쓸 최후의 보루 |

근거: `module_utils/adapter_common.py:280-288`(①②), `:243-244` + `:150-154`(③).

### 12-5. [설명 포인트] "설정표 없는 장비"가 처리되는 방식

새 제조사 장비가 설정표 없이 들어왔다고 하자.

1. 제조사 이름을 못 알아본다 → "미확인"으로 처리
2. 설정표 31개를 전부 훑는다
3. 제조사 조건이 걸린 설정표는 **규칙 ①로 전부 탈락**
4. **범용 설정표만 남는다** (조건이 없어서 항상 통과, 점수 −400)
5. 후보가 1개이므로 그것이 1등 → 선택됨
6. 금고 지정이 비어 있어 금고를 열지 않고, 제조사 전용 절차도 없어 그 단계를 건너뛴다
7. **표준 방식으로 얻을 수 있는 만큼 수집한다**

> **설명 포인트**: 이것이 "예외 처리 코드"가 아니라는 게 우아한 점이다. `if 설정표 없으면
> 범용을 써라` 같은 코드가 없다. **범용이 항상 최하점으로 후보에 있다가, 나머지가 다 탈락하면
> 자동으로 1등이 되는** 것뿐이다. 정렬의 자연스러운 결과다.

> **작도 참고**: "후보 목록" 상자 안에 점수순 막대를 그리고, 맨 아래 −400 자리에 범용을 두면
> 이 개념이 그림 하나로 전달된다.

### 12-6. 새 세대 추가 = 파일 1개

예: Dell 의 다음 세대 관리 칩이 나왔다.

| # | 할 일 |
|---|---|
| 1 | `adapters/redfish/dell_idrac11.yml` 한 개 만들기 (우선순위를 기존 최고값보다 높게, 모델·펌웨어 조건으로 구세대와 안 겹치게) |

**끝이다.** 제조사 이름 표준화 표, 금고, 제조사 전용 절차는 전부 재사용된다.
선택기가 폴더 전체를 훑기 때문에 파일을 놓기만 하면 인식된다(`adapter_loader.py:106`).

### 12-7. 새 제조사 추가 = 파일 4개, 코드 0줄

| # | 파일 | 필수 | 내용 |
|---|---|---|---|
| 1 | `adapters/redfish/<제조사>_<칩이름>.yml` | 필수 | 설정표 |
| 2 | `common/vars/vendor_aliases.yml` | 필수 | 제조사 이름 표기 변형들을 표준 이름에 매핑 |
| 3 | `vault/redfish/<금고이름>.yml` | 인증 필요 시 | 계정 정보 |
| 4 | `redfish-gather/tasks/vendors/<제조사>/collect_oem.yml` + `normalize_oem.yml` | 전용 수집 쓸 때만 | 제조사 전용 절차 |

**고치지 않아도 되는 것** (코드로 검증됨):

| 대상 | 왜 안 고쳐도 되나 |
|---|---|
| 작업 절차서 (`site.yml` 3벌) | 제조사 이름이 하나도 없음. 전용 절차 실행 여부도 **설정표 값**으로 판단(`redfish-gather/site.yml:140`) |
| 설정표 목록 파일 (`adapters/registry.yml`) | **이 파일을 읽는 실행 코드가 없다.** 폴더를 직접 훑는다. "등록해야 인식된다"는 것은 사실이 아님 |
| 파이프라인 (`Jenkinsfile*`) | 제조사와 무관 |
| 결과 형식 정의 (`schema/`) | 제조사와 무관 |
| 금고 경로 | 코드에 나열돼 있지 않고 **설정표 값으로 조립**된다(`redfish-gather/tasks/load_vault.yml:31`) |

> **예외 1건**: 새 장비가 "여러 노드를 한 관리 칩이 대표하는" 특수 구성이면, 그 구성 종류가
> 절차서에 2가지만 적혀 있어서(`redfish-gather/site.yml:200-204`) 세 번째 종류가 필요하면
> 절차서 수정이 필요하다.

### 12-8. 실제 우선순위 분포 (관리 칩 경로 31개, 실측 2026-08-10)

| 우선순위 | 설정표 | 성격 |
|---|---|---|
| 0 | `redfish_generic` | 범용 최후 보루 |
| 10 | `cisco_bmc`, `dell_idrac`, `hpe_ilo`, `lenovo_bmc`, `supermicro_bmc` | 제조사만 알고 세대 모를 때 |
| 50 | `dell_idrac8`, `hpe_ilo4`, `lenovo_imm2`, `supermicro_x9` | 구세대 |
| 75~90 | `supermicro_x10`(75), `fujitsu_irmc`·`huawei_ibmc`·`inspur_isbmc`·`quanta_qct_bmc`·`supermicro_ars`(80), `hpe_ilo5`(90) | 중간 세대 / 세대 구분 없는 제조사 |
| 100~102 | `cisco_cimc`, `dell_idrac9`, `hpe_ilo6`, `lenovo_xcc`, `supermicro_x11/x12/x13`(100), `hpe_superdome_flex`(101), `hpe_csus_3200`(102) | 현행 주력 |
| 110~120 | `cisco_ucs_xseries`·`supermicro_x14`(110), `dell_idrac10`·`hpe_ilo7`·`lenovo_xcc3`(120) | 최신 세대 |

> **주의**: "세대가 새로울수록 숫자가 크다"는 것은 42개 파일에서 관찰한 **관행이지 강제 규칙이
> 아니다**(추정). 이를 규정한 코드는 없다.

같은 우선순위끼리(예: supermicro 100번대 3개)는 모델 조건이 서로 배타적이라 실제로는 동점이
나지 않는다. 만에 하나 동점이면 **파일명 알파벳 순으로 앞선 것**이 이긴다
(`adapter_loader.py:106`, `:234-238`).

### 12-9. [보충] 제조사 이름이 등장할 수밖에 없는 곳

"코드에 제조사 이름이 없다"에는 예외가 있다. 관리 칩 표준 규격 자체가 **"제조사 전용 영역"을
제조사 이름으로 구분하도록 정의**하고 있어서, 그 영역을 읽는 부분에는 이름이 나올 수밖에 없다
(`redfish-gather/library/redfish_gather.py` 안의 제조사 전용 영역 추출부).

다만 이것은 **수집 도구 내부에 국한**되고, 작업 절차서·선택기에는 전혀 없다.

### 13-6. 직선 구간 vs 분기 구간

| 구간 | 형태 |
|---|---|
| 전체 큰 그림 (2장) | **완전 직선** |
| 파이프라인 검증 | 직선 + 조기 종료만 |
| 파이프라인 회신 | 직선 + 반복 1개 |
| 가상화 호스트 경로 | **거의 완전 직선** (중단 분기만) |
