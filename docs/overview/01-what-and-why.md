# 이 시스템이 푸는 문제

## 상황

데이터센터에 서버가 수백 대 있다고 합시다. 자산 관리든 용량 산정이든 각 서버에 CPU가 몇 개이고 메모리가 얼마이며 디스크가 어떻게 붙어 있는지 알아야 합니다.

문제는 그 정보를 꺼내는 방법이 장비마다 다르다는 점입니다. Linux면 SSH로 들어가 `dmidecode`를 읽고, Windows면 WinRM으로 `Get-CimInstance`를 부르고, VMware ESXi면 vSphere API를 씁니다. 서버 전원이 꺼져 있어도 정보를 봐야 한다면 BMC(관리 컨트롤러)에 Redfish API로 물어야 하는데, 이 응답은 제조사마다 다릅니다. Dell의 iDRAC과 HPE의 iLO는 같은 표준을 따르면서도 세부 경로와 필드가 갈립니다.

그래서 조회하는 쪽이 이 모든 차이를 알아야 하고, 벤더가 하나 늘 때마다 조회하는 코드도 같이 늘어납니다.

## 이 시스템이 하는 일

server-exporter는 그 차이를 안으로 숨깁니다. 호출자는 IP 하나와 종류만 알려주면 됩니다. 돌려받는 것은 어떤 경로로 갔든 똑같이 생긴 JSON입니다.

```text
호출자:  "192.0.2.10 이고, 종류는 os 입니다"
        ↓
        (SSH로 접속할지 WinRM으로 갈지, 어느 명령을 쓸지는 안에서 정합니다)
        ↓
응답:    { "status": "success", "data": { "cpu": {...}, "memory": {...}, ... } }
```

Redfish 경로도 마찬가지입니다. 제조사가 Dell인지 HPE인지는 BMC에 직접 물어서 알아내고 거기에 맞는 수집 방식을 골라 씁니다. 호출자는 제조사를 몰라도 됩니다.

## 세 가지 약속

호출자는 IP만 보냅니다. 자격증명도, 호스트명도, 제조사도 호출자 책임이 아닙니다. 계정은 저장소 안의 암호화된 vault에 있고 OS 종류와 BMC 제조사는 파이프라인이 직접 확인합니다. 이것은 편의가 아니라 보안 문제입니다. 자격증명이 호출 경로를 타고 흐르지 않습니다.

응답 모양은 어떤 상황에서도 같습니다. 장비가 꺼져 있든, 인증이 막히든, 일부 항목만 실패하든 같은 13필드 봉투가 나옵니다. 호출자는 `status`와 `errors`만 보고 분기하면 되고, "응답이 아예 안 왔을 때"를 따로 처리할 필요가 없습니다.

새 벤더는 코드를 고치지 않고 늘립니다. 벤더별 차이는 YAML 파일(어댑터)에 적습니다. 수집 코드와 파이프라인은 벤더 이름을 모른 채로 남습니다.

## 어디까지 하고 어디부터 안 하나

수집만 합니다. 장비 상태를 바꾸지 않습니다. 전원을 끄거나 설정을 쓰지 않습니다.

한 가지 예외가 Redfish 계정입니다. 수집용 표준 계정으로 BMC에 못 들어가면 복구 계정으로 들어가 표준 계정을 되살리는 경로가 있습니다. 수집을 계속하기 위한 최소한의 쓰기이고 들어가는 조건이 엄격합니다. 자세한 내용은 [operate/05-vault.md](../operate/05-vault.md)에 있습니다.

수집 결과를 저장하지도 않습니다. JSON을 만들어 돌려줄 뿐이고 보관은 호출자 몫입니다.

대상은 IPv4 주소입니다. 호스트명으로 찾거나 IP 대역을 훑어 장비를 발견하는 기능은 없습니다. 어떤 IP를 조회할지는 호출자가 안다고 전제합니다.

## 세 갈래 경로

| 종류 | 어디에 접속하나 | 언제 쓰나 |
|---|---|---|
| `os` | 서버에 직접 (Linux는 SSH 22, Windows는 WinRM 5986 또는 5985) | OS가 떠 있고 그 안의 정보가 필요할 때 |
| `esxi` | 하이퍼바이저의 vSphere API (443) | VMware 호스트일 때 |
| `redfish` | BMC의 Redfish API (443) | 하드웨어 정보가 필요하거나, OS가 꺼져 있어도 봐야 할 때 |

같은 물리 서버를 `redfish`로도 `os`로도 조회할 수 있습니다. 실제로 그렇게 해 보면 `correlation.serial_number`가 같은 값으로 나옵니다. 두 경로가 결국 같은 하드웨어의 SMBIOS를 읽기 때문입니다. 다만 읽는 원본 필드는 서로 다르므로 자세한 사정은 [contract/02-output-envelope.md](../contract/02-output-envelope.md)를 보세요.
