# ADR-2026-11-09 — 승격 체인 전 GitHub 저장소 공개 확인 · 장시간 실행은 분리 프로세스로

- 상태: Accepted (2026-11-09, 사용자 지시 — 아래 기록)
- 관련: rule 80 R7 · R8(신설) · rule 93 R2 예외 2 · rule 24 R9 · `scripts/ai/longrun/` · `tests/unit/test_longrun.py` ·
  `docs/ai/catalogs/FAILURE_PATTERNS.md` 2026-11-07 · 2026-11-09 · `docs/operate/09-production-branch.md` 4절

## 컨텍스트 (Why)

### 저장소 공개 범위

- `Jenkinsfile_ci` 의 Prodgen Drift(`git fetch origin production`) · Prodgen Verify(G20 `ls-remote`)는 자격 없이 GitHub 를 읽는다.
  Job checkout 은 Job 자격을 쓰지만 이 두 셸 단계는 그렇지 않다.
- 사용자는 평소 GitHub 저장소를 비공개로 둔다. 그래서 승격 CI 가 두 번 같은 이유로 실패했다.
  - 2026-11-07 CI #66: `fatal: could not read Username for 'https://github.com'`
  - 2026-11-09 CI #68: 같은 오류. AI 가 빌드를 멈췄고 Harness 빌드는 0건이었다
- 두 번 모두 사용자가 공개로 바꾼 뒤 같은 SHA 로 다시 돌렸다(CI #67 · #69).
- 영구 해결(두 단계를 자격으로 감싸기)은 `docs/ai/NEXT_ACTIONS.md` 2026-11-07 MED 항목으로 남아 있다.

### 메모리 압박과 백그라운드 셸 정리

- 시스템 메모리가 부족해지면 Claude Code 는 백그라운드 셸을 정리한다. 그 셸이 잡고 있던 실행도 함께 끝난다.
  - 2026-10-15 · 2026-10-28: 전체 pytest 와 WSL gate 를 겹쳐 돌리다 중단
  - 2026-11-09: 승격 체인(매트릭스 · CI · promote · canary)이 CI #68 을 기다리는 동안 정리됐다.
    여유 메모리는 32 GB 중 약 4 GB 였고, 대기 자체는 가벼운 폴링이었다(메모리를 많이 쓴 프로세스는 확인하지 않았다)
- 다시 시작할 때마다 진행 상태를 손으로 맞춰야 했다. 어느 빌드가 이미 들어갔는지 모르면 빌드를 중복으로 넣을 위험이 있었다.

### 사용자 지시 (2026-11-09 대화)

> "다음에도 할때 나한테 public으로변경해달라고 요청하고 작업끝나서 private라면 public으로다시 바꾸라고 말하도록 하네스에 저장해주세요.
> 그리고 매번 메모리때문에 실패했다고하는데 이것도 실패하지않는 법을 채택해서 하네스에 저장해주세요."

- 앞 문장의 뒷부분은 "작업이 끝나면, 원래 비공개였다면 다시 **비공개**로 바꾸라고 안내" 로 읽었다.
  - 작업 중에는 공개 상태이므로 "공개로 다시 바꾸라" 는 할 일이 없다.
  - 사용자가 평소 비공개로 둔다는 사실과도 맞는다.
- 이 해석은 사용자에게 밝혔다(지시 직후 답변과 완료 보고).

## 결정 (What)

1. **공개 확인 (rule 80 R7)**
   - 승격 체인을 시작하기 전에 CI 와 같은 방식으로 저장소를 읽어 본다(자격 없는 `git -c credential.helper= ls-remote <SCM 주소>`).
   - 비공개면 체인을 시작하지 않고 사용자에게 공개 전환을 요청한다.
   - 끝나면, 시작할 때 비공개였을 경우 다시 비공개로 바꾸라고 완료 보고에 적는다(rule 24 R9).
   - AI 는 공개 범위를 직접 바꾸지 않는다.
2. **분리 실행 (rule 80 R8)**
   - 수십 분 넘는 대기와 무거운 로컬 실행은 Claude Code 백그라운드 셸이 아니라 분리 프로세스로 띄운다.
     - Windows: 새 프로세스 그룹 · 창 없음 · 가능하면 job object 이탈
     - Linux: 새 세션
   - 진행은 작업 폴더 파일(`state.json` · `run.log` · `detached_*.log`)로만 본다.
3. **빌드 기록 · 이어받기**
   - Jenkins 빌드 번호를 얻자마자 journal(`runs_*.jsonl.started`)에 남긴다.
   - 다시 실행하면 이어 돌리기가 기본이다.
     - 기대대로 끝난 빌드는 그대로 둔다.
     - journal 에만 있고 아직 돌거나 기대 결과로 끝난 빌드는 새로 넣지 않고 기다린다.
     - 다른 결과로 끝난 빌드는 새로 넣는다.
   - 예외: 투입 시점 관측이 증거인 시나리오는 이어받지 않는다.
     - E2E-A2: 투입 전후 origin main tip 관측
     - T5: 시작 표지를 본 뒤 10초에 중단
4. **파일 감시**
   - Monitor 는 `watch` 로 로그의 새 줄만 읽는다. 읽은 위치를 `watch_offset.txt` 에 남긴다.
   - 감시가 끊기면 같은 명령으로 다시 건다. 빠짐 · 중복이 없고, 실행은 감시와 무관하게 계속된다.
5. **도구를 저장소에 둔다** — `scripts/ai/longrun/`(개발 전용 — production 생성 대상 아님)
   - 이번 승격에 쓴 임시 스크립트를 옮겼다.
     - `detached.py`: 분리 실행 · 생존 확인 · 감시
     - `jenkins.py`: crumb · 쿠키 세션 · 투입 · 대기 · 중단
     - `submit.py`: journal · 이어받기
     - `bodies.py`: 봉투 대조
     - `chain.py`: 승격 체인
   - 바꾼 것은 세 가지다.
     - 경로 · 빌드 번호 · Job 이름은 계획 파일로 받는다.
     - 시나리오 기대 결과는 prodgen 계약(`MAIN_CONTRACT`)에서 가져온다.
     - 작업 폴더 기본값은 세션이 바뀌어도 남는 `~/.se_longrun/promote-<sha8>` 이다.
   - 체인이 끝나면 다음 승격용 `next_plan.json` 을 쓴다.
6. **Jenkins TLS 고정 (승격 뒤 보강)**
   - 도구의 모든 curl 호출은 고정한 인증서(`~/.se_longrun/jenkins_chain.pem`)를 `--cacert` 로 넘겨 검증한다. `-k` 는 쓰지 않는다.
   - 인증서는 `pin-cert` 가 받아 기대 지문과 같을 때만 저장한다. 파일이 없으면 preflight 가 네트워크 확인 전에 멈춘다.
   - 계기: 이번 승격의 임시 스크립트(매트릭스 · CI · canary)가 prodgen 의 Jenkins 읽기(`curl -sk`)를 본떠 `-k` 로 돌았다.
     2026-11-07 승격은 서버 인증서를 받아 지문을 확인하고 `--cacert` 로 검증했다.
     승격 뒤 받은 인증서 지문은 2026-11-07 기록과 같았다(`B0:9E:…:A3:16`). 실행 중 연결이 그 서버였는지는 확인할 수 없다.
   - prodgen 자체의 `curl -sk`(`evidence.py` · `verify/__init__.py` · `verify/gates_live.py`)는 이번 범위가 아니다(NEXT_ACTIONS).

## 결과 (Impact)

- 제품 코드 · 배포본(production tree) 변경 없음
  - `scripts/ai/` 는 `production_manifest.yml` 의 제외 경로다.
  - 시험은 `source_text` 표식이라 G14 overlay 에서 빠진다.
- 승격 체인 시작에 사용자 대화가 한 번 생긴다(비공개일 때만). rule 93 R2 예외 2 의 "per-instance 승인 불요" 는 그대로다.
  - 공개 요청은 승인 요청이 아니라 사용자만 할 수 있는 설정 작업의 요청이다.
- 셸이 정리되면 분리 실행은 계속되고 감시만 다시 건다. 실행 자체가 죽었으면 같은 명령으로 다시 실행해도 빌드가 중복으로 들어가지 않는다.
- 남는 위험
  - 분리 프로세스도 시스템 메모리를 쓴다. promote 단계는 이 PC 에서 G14 · G15 · G19 를 돌리므로, 그동안 다른 무거운 실행을 겹치지 않는다(R8 Forbidden).
  - 분리 프로세스가 도는 동안 Claude Code 세션이 끝나도 실행은 이어진다. 다음 세션은 `status --work <폴더>` 로 이어서 본다.

## 대안 비교 (Considered)

| 대안 | 채택 여부 | 이유 |
|---|---|---|
| `Jenkinsfile_ci` Drift · Verify 를 자격으로 감싸 공개 요구 자체를 없앤다 | 이번에는 아님 | 보호 경로(`Jenkinsfile*`) 변경이고 CI 회귀가 필요하다. 이미 NEXT_ACTIONS MED 로 등록 — 반영되면 R7 을 지운다 |
| AI 가 GitHub 공개 범위를 API 로 바꾼다 | 아니오 | 저장소 설정은 사용자 몫이다. 비공개는 사용자의 운영 선택이다 |
| 백그라운드 셸 정리 끄기(`CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP`) | 아니오(AI 측) | 사용자 설정이다. 끄더라도 메모리 압박 자체는 남고, 셸이 다른 이유로 끝나면 같은 문제다 |
| 전경 실행으로 끝까지 기다린다 | 아니오 | 도구 호출 시간 한도(10분)를 넘는 대기가 있다(CI 약 1시간) |
| Windows 작업 스케줄러 · 서비스로 띄운다 | 아니오 | 시스템 설정 변경이 필요하다. 분리 프로세스는 호출한 셸이 끝난 뒤에도 살아 있었다(2026-11-09 분리 실행 시험 · 이번 승격 체인의 CI 단계부터 사용) |
| 임시 스크립트를 세션 scratchpad 에만 둔다 | 아니오 | 세션마다 다시 써야 했고(2026-10-19 · 11-07 · 11-09), 그때마다 인코딩 · 쿠키 · 중단 시점 실수가 났다 |
| Jenkins 호출은 prodgen 처럼 `-k` 로 둔다 | 아니오 | 자격을 실어 보낸다. 서버 인증서는 자체 서명 1장이라 고정이 간단하고, 2026-11-07 에 이미 그 방식으로 돌았다 |
| 인증서를 처음 받을 때 지문 대조 없이 저장한다 | 아니오 | 처음 받는 연결이 바뀐 서버면 그 인증서를 믿게 된다. 기록된 지문(rule 80 R8)이나 사용자 확인과 대조한다 |
